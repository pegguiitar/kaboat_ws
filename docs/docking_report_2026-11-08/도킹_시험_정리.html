1. 현재 결과와 문서 기준

작성 시각: 2026-11-08T01:12:39+09:00. 브랜치 feature/docking-real, 기준 HEAD e768828c764dc8d6c82e482060fa23c3c6900f10. 이번 세션의 코드 변경은 미커밋 상태다. 현재 소스와 설정 사본을 code_snapshot 폴더에 함께 보관했다.

실제 모터 구동과 B-spline 경로 추종, 진입점 3m 이내에서 노란 최종 목표로 전환하는 동작까지 확인했다. 최종 도킹 완료(FINISHED)와 무충돌 접안은 아직 확인하지 못했다. 마지막 시험은 최종 목표 관측 지연으로 정지했다.

사용자는 진입점 근처에서 목표가 부정확해져 실제 충돌했다고 보고했다. 접촉 시각·좌표·충돌 물체를 로그만으로 확정하지는 못했다. 추종이 진행됐다는 사실을 도킹 성공으로 해석하면 안 된다.

최신 설정: 목표 위치/법선의 시간 평균 0초, 최신 유효 관측 한 개 사용. 진입점 3m 이내에서 /dock/stop_point로 전환, 최종 단계 목표 갱신 지속. 현재 모터는 중립이며 출발 대기다. 이 문서 생성 중 실제 주행 명령은 보내지 않았다.

2. 실행 구조와 좌표 규약

D455 RGB → YOLO 마스크 → 깊이와 무관한 광학 방위 ray
                                  ↓
선체 LiDAR /scan → 방위 부근 RANSAC 벽선 → 교점 + 수조 안쪽 법선
                                  ↓ 측정 시각 TF
                    odom 벽 좌표 + 단위 법선
                                  ↓ 현재는 평균 없음
             진입점 / 정렬점 / 노란 최종 정지점
                                  ↓
occupancy_grid → DRI → B-spline generate/check/repair → 기존 LOS형 follow_cmd
                                  ↓
                         /cmd_vel → thruster_driver
                                  ↓ 115200 baud, LLLLRRRR + LF
                      MCU 컴퓨터 모드 → 좌우 ESC PWM

외벽 라이다의 /boat_pose와 GQ7 IMU를 indoor_lidar_odom이 받아 /odom 및 odom→base_link TF를 만든다. 이 배 위치 추적 입력은 노트북에서 별도로 유지해야 한다. 최종 목표와 경로는 odom 기준이며, base_link 시각화 토픽은 선체 상대값이다.

변환/항목현재 설정
base_link → onboard_laser_frame(+0.73, 0, 0)m; 장착 회전 0 가정
onboard_laser_frame → camera_link(-0.73, 0, +0.63)m; 장착 회전 0 가정
base_link → camera_link 합성(0, 0, +0.63)m; 카메라는 라이다보다 73cm 뒤
카메라 optical TFD455 드라이버가 제공
목표/지도/경로 좌표odom; 평면 투영 point.z=0
pitch 필터-1.2° ~ +4.0°; /scan 및 occupancy 처리. /scan/raw는 원본
roll 필터±3° (현재 런치 설정)
수조 경계odom x=0..10m, y=0..5m, 정지 여유 0.5m
스테이션 법선 사전값odom +X 방향 [1,0]; 좌표계 회전 시 다시 확인 필요

카메라 촬영 시각에 가장 가까운 라이다 스캔을 선택한다. ray/scan 허용 차이는 0.12초. 서로 다른 측정 시각의 상대 운동은 lookup_transform_full(..., fixed_frame=odom)로 보정한다. 보정 TF가 없을 때는 시각 차이 0.035초 이내에서만 정적 변환으로 대체한다. odom 변환은 라이다 측정 시각을 쓴다.

따라서 시간 보정이 전혀 없는 구현은 아니다. 그러나 TF/odom 자체가 부정확하거나 벽선 연결이 바뀌면 고정된 스테이션의 odom 목표가 이동할 수 있다. 설치 회전 0 가정과 실제 시야-라이다 각도 정합은 별도 정밀 검증이 남아 있다.

3. 목표 생성과 현재 제어 상태 전환

현재 선택 목표는 triangle이다. triangle/circle/square 모두 방위와 벽 교점·법선·투영점을 계산하지만, 제어는 선택 목표 한 개를 사용한다. depth 측정은 진단용으로 남아 있고 현재 도킹 목표 위치 생성에는 카메라 depth를 쓰지 않는다.

wall = 선택 마커의 카메라 ray와 LiDAR 벽선 교점 (odom)
n = 벽에서 수조 안쪽/선박 쪽을 향하는 단위 법선
STOP(노랑) = wall + 1.0m × n
ALIGN(주황) = wall + 1.5m × n
ENTRY(하늘색) = wall + 2.0m × n  # 명목값, DRI 검색으로 조정 가능
추정 marker = wall - 1.0m × n  # 벽 뒤 1m 가정의 시각화 좌표

사용자가 선택한 “벽 뒤 1m 마커에서 안쪽으로 1m 당기기 = 벽선 위 목표”라는 중간 합의와 달리, 현재 실행 코드의 STOP은 벽선보다 수조 안쪽 1m이다. 현재 실제 런치 dock_stop_distance_m=1.0을 기준으로 문서화했다. 두 의미를 혼동하지 말아야 한다. 이 보고서 작성 중 목표 오프셋은 변경하지 않았다.

명목 진입 경로가 안 나오면 기존 DRI를 사용해 진입점을 법선 축 방향으로 0.15m씩, 최대 ±1.5m 범위에서 검색한다. 노란 STOP 좌표는 이 검색으로 옮기지 않는다. 현재는 approach_only_entry_search=true이며 진입점까지의 충돌 회피 가능성을 평가한다.

상태목표 갱신 및 제어
WAIT/PREVIEW신선한 센서·목표와 유효 경로를 확보한다. /dock/start 전에는 모터 명령 0.
ENTRY출발 시 진입점을 고정해 기존 DRI/B-spline 회피 추종. 이 단계는 마커 갱신 중단만으로 즉시 정지하지 않는다.
전환 조건현재 선체 위치와 출발 때 고정한 진입점 사이 거리 ≤3.0m. 최신 진입점과의 거리를 쓰는 것은 아니다.
FINAL신선한 노란 /dock/stop_point로 목표 변경. 이후 ENTRY로 되돌아가지 않는다. 목표 수신값을 제어 tick에서 반영한다.
FINAL 경로 갱신전환 시 또는 경로 생성 기준 목표에서 ≥0.10m 변하면 FSM/경로를 초기화해 재생성한다.
FINAL 정지목표 관측/수신이 0.7초를 넘기면 정지. 직전 제어 목표보다 한 번에 0.5m 넘게 바뀌어도 정지.
도착현재 활성 목표까지 ≤0.25m면 FINISHED 및 중립. 최종 선수 방향과 속도까지 포함한 접안 완료 판정은 아니다.
회피 실패수리·재생성 실패 후 ESCAPE가 필요하면 정지. allow_escape=false이므로 자동 후진하지 않는다.

현재 /dock/waypoints의 세 pose를 순서대로 추종하는 모드는 비활성이다(dock_waypoints_topic 빈 문자열). ALIGN은 시각화 좌표이며 독립 제어 단계가 아니다. 최종 선수각을 법선 방향으로 강제 고정하는 동작도 현재 FINAL 경로에는 없다. 일반 B-spline/LOS형 추종으로 노란 점을 향한다.

goal_average_window_s=0.0은 목표 생성기의 벽 위치와 법선 시간 평균을 모두 끈다. RANSAC, 벽 방향 사전값·이전 벽 이력(1.5초), depth 진단 필터, 입력 시각 검사는 유지된다. 목표 생성기는 10Hz timer지만 새 측정 시각이 있는 유효 관측만 제어기에 새로 반영된다.

5. 필요한 프로세스·토픽과 실행 명령

토픽은 따로 “켜는” 것이 아니라 해당 노드를 시작하면 발행된다. 기본 순서는 외벽 위치 추적/브리지 → IMU·선체 LiDAR·odom → D455/YOLO/TF → 모터 드라이버 → 목표·지도·도킹 제어기다.

현재 보존한 trial_monitor_60s.py는 이번 시험용 보조 스크립트다. 유효 경로를 기다린 뒤 시작 서비스를 호출하고, 시작 후 최대60초 관측한 다음 정지한다. 컨트롤러 자체의 60초 제한이 아니다. 직접 /dock/start만 호출하면 이 관측 시간 제한은 적용되지 않는다. 모니터와 직접 시작 서비스를 동시에 실행하지 않는다.

목표와 경계/좌표 의존10×5m 경계와 +X 법선 사전값 고정외벽 라이다 원점/방향을 바꾸면 관련 파라미터와 TF를 함께 재검증.

앞선 bring-up 단계에서는 부팅 후 D455/센서/TF/검출 노드를 다시 띄워야 하는 상태, 원본 RGB 구독 부담, 저속 debug_image와 실제 YOLO 추론 빈도의 혼동도 있었다. 현재는 TensorRT/GPU 설정과 스트림 크기를 명시한다. 과거의 모든 끊김을 CPU 추론 또는 D455 하드웨어 고장으로 확정한 것은 아니다. 카메라/라이다 장착 좌표는 사용자 수정값을 반영한 현재 합성 위치를 기준으로 한다.

DRI 계산에서는 Gaussian 영향 범위 캐시로 계산량을 줄였으며 위험도 수식/안전 기준 자체를 완화한 것은 아니다. DRI remap 이후 구독자 수 검사 문제는 실제 publisher의 구독자 수를 조회하도록 수정했다. 지도는 기존 /avoid/dri, /avoid/dri_marks를 유지한다. /dock/lidar/markers의 길게 보이는 벽 직선은 시각화이며 그 선분 전체를 occupancy_grid에 장애물로 추가하는 구조는 아니다.

현재 중요한 다음 확인은 이동 중 wall_point_base와 normal_base가 안정적인데 odom 값만 달라지는지, 아니면 선체 상대 관측부터 벽 연결이 바뀌는지의 분리다. 동시에 ray/scan 시각 차이, compensated 플래그, TF, /boat_pose, /odom, 활성 목표, 경로, 실제 PWM을 같은 시각축으로 기록해야 한다. 작은 목표 변동을 무조건 추종하는 정책과 단순 stale timeout 증가는 해결책으로 확정되지 않았다.

9. 현재 제어와 기존 LOS의 실제 차이

현재 도킹과 LosFollower는 둘 다 avoid_fsm.follow_cmd()를 호출한다. 따라서 “B-spline 제어 대신 LOS로 바꾸면 다른 기본 조향기가 된다”는 해석은 맞지 않는다. B-spline은 경로 형태/생성 방법이고, 현재 그 경로를 추종하는 방법 자체가 lookahead 기반 LOS형 조향이다.

target = 경로 진행 위치에서 lookahead만큼 앞선 샘플
heading_error = wrap(atan2(target_y-boat_y, target_x-boat_x) - yaw)
angular_cmd = Kp * heading_error - Kd * yaw_rate
v = clamp(omega_max / max_curvature_ahead, v_min, v_max)
v *= min(distance_to_goal / slow_radius, 1)
linear_cmd = cmd_full * (v / v_full) ** cmd_exp
# 큰 선수각 오차에서는 추가 속도 제한, 최종 명령은 각각 상한으로 clip
